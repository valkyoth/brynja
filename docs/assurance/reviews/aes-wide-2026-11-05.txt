Findings

1. Medium: constant-time behaviour is only verified at the IR level, not in the machine code

- Location: crates/brynja-crypto/src/aes/portable/field.rs:6, :13; it now also protects the new key schedule in portable/wide.rs:23-44.
- Type: side channel (timing).
- Description: The S-box is computed with masks like 0u8.wrapping_sub(b & 1), which is constant-time in source but not guaranteed after code generation. LLVM can turn these into branches or cmov-less selects on some targets and optimization levels. The timing evidence is weak against a strong attacker:
  - check-aes-dataflow.py inspects LLVM IR, not the final linked machine code.
  - brynja-aes-wide-timing compares only two fixed classes (all-0x00 vs all-0xff) with 512 samples.
  - AES-192/256 add new secret-dependent work (SubWord on key bytes, including the extra AES-256 SubWord), and none of it has machine-code-level evidence yet.
- Remediation: Add a value barrier on the masks, and add a check on the final linked binary that rejects conditional branches or memory lookups indexed by secrets in multiply, xtime, sbox, inv_sbox and the wide expand/transform, per target. Also run a dudect-style fixed-vs-random test with at least 10⁶ samples before calling this qualified.
#[inline(always)]
fn barrier(x: u8) -> u8 {
    // Opaque to the optimizer; prevents mask-to-branch rewriting.
    core::hint::black_box(x)
}
pub(super) fn xtime(a: u8) -> u8 {
    (a << 1) ^ (0x1b & barrier(0u8.wrapping_sub(a >> 7)))
}
  black_box is best-effort, so the binary-level check is still the real control.

2. Medium: no fault-injection countermeasure (relevant for a military threat model)

- Location: crates/brynja-crypto/src/aes/portable/wide.rs:60-89.
- Type: missing protection against physical attack (differential fault analysis).
- Description: A single induced fault in the last rounds lets an attacker recover round keys. For AES-256, two consecutive recovered round keys give the whole master key. The docs say physical attacks are out of scope, which is acceptable for a library. But nothing in the API lets a high-assurance user opt into a defense.
- Remediation: Add an optional encrypt-and-verify path that releases output only if a recomputation matches:
pub fn encrypt_block_verified<'out>(&self, input: &[u8; 16], output: &'out mut [u8; 16])
    -> Result<SecretBlock<'out>, Error> {
    let destination = SecretRegionInitialization::begin(output)?;
    let mut a = Scratch::<16>::new(); a.0.copy_from_slice(input);
    wide::transform::<K, S, R>(&mut a.0, schedule, false)?;
    let mut b = Scratch::<16>::new(); b.0.copy_from_slice(&a.0);
    wide::transform::<K, S, R>(&mut b.0, schedule, true)?;      // decrypt back
    let diff = b.0.iter().zip(input).fold(0u8, |d, (x, y)| d | (x ^ y));
    if core::hint::black_box(diff) != 0 { return Err(Error::SecretMemory); } // output cleared on drop
    /* destination.write(&a.0)?; finish */
}

4. Low: the ephemeral key types cost a lot of CPU per block

- Location: crates/brynja-crypto/src/aes/wide.rs:81-92, :95-104.
- Type: denial of service through CPU cost.
- Description: Aes192Key/Aes256Key rebuild the full 208/240-byte schedule on every blockout 15 field multiplications of 8 steps each. With 14 rounds plus key expansion forAES-256, the cost per block is large. An attacker who controls how many blocks are processed gets a strong CPU amplifier. The docs warn about this, but nothing in the API limits it.
- Remediation: Point protocol-facing code to Aes*ExpandedKey. Also consider a #[doc] warning plus a lint or policy check in the protocol crates that rejects the ephemeral types inside per-message loops.

6. Low: the OpenSSL test oracle is found through PATH

- Location: crates/brynja-crypto/tests/aes_wide_differential.rs:23, :74.
- Type: test-integrity / supply chain.
- Description: Command::new("openssl") runs whatever openssl comes first on PATH. A poisoned CI image could supply a fake oracle that agrees with a broken implementation. The KATs limit the damage, but the differential test exists to be independent evidence.
- Remediation:

## Implementation verdict

The reviewed implementation appears correct within its deliberately narrow raw-block boundary:

- No unsafe code, raw pointers, manual Send/Sync, transmutation, unchecked indexing, or production unwrap/expect.
- AES-192 and AES-256 schedule lengths, key dependencies, AES-256 extra SubWord, and 12/14-round transformations match FIPS 197.
- Fixed-width arrays and private const-generic instantiations prevent width/round confusion.
- Key, expanded schedule, state, word, and output owners clear their admitted storage on success, error, unwind, explicit clear, and ordinary drop.
- Public ciphertext is staged and copied only after successful completion.
- Owners are non-Copy, non-Clone, non-Debug, non-Send, and non-Sync.
- Runtime work and memory consumption are fixed per block; no attacker-controlled allocation or unbounded loop was introduced.
- The dependency delta introduces no third-party dependency. The lockfile only changes the façade version. The sole registry dependency in the workspace, sanitization 2.1.1, returned no known advisory from the current OSV query; absence of a known advisory is not an independent source audit.
