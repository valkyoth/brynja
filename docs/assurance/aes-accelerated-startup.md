# Accelerated static ARM startup review

This v0.27.3 development check reviews a package-external static ARM startup
boundary on Rust 1.90.0 and 1.99.1, direct/facade routes, abort/unwind, with
opt-level 3, fat LTO, one codegen unit and overflow checks. It uses QEMU, not
native ARM qualification. Hosted admission and x86 startup remain separate work.
It is not a publication gate or a physical fault-resistance claim.

## Reviewed behavior

`assurance/aes-accelerated-campaigns/startup.rs` wraps the public
`Authority::new` in a non-inlined package-external function returning an optional
owner. It neither changes library inlining nor injects a production detector.
Opaque calls exercise both valid enum values. The wrong-architecture request
returns no owner before expansion or round instructions; an admitted ARM
request returns an owner with generation 2 and healthy or quarantined state.
Normal execution also tests all three caller-owned cached key widths, clearing,
and terminal quarantine. These opaque caller-key operations prevent LTO from
specializing the round kernels to the public startup schedules alone.

The complete startup bodies were inspected before pinning: 196 instructions on
1.90.0 and 193 on 1.99.1. Each has twelve direct calls (three expansions, three
schedule comparisons and six round calls), two local branches, three direct
constant loads and seven additional reference addresses. Both panic strategies
and both package routes match the respective compiler policy after relocation
binding. No runtime/unwind call is present in these startup bodies.

The wrong-backend branch precedes all twelve calls. The admitted path initializes
176/208/240-byte temporary schedules, constructs sequential 16/24/32-byte public
keys, executes all three expansions, and compares their complete output against
fixed expected schedules. Block tests use the fixed schedules independently of
the calculated expansion output. Each encryption starts at the fixed plaintext;
each decryption starts at its independent fixed ciphertext, not the calculated
encryption result. Direction operands are zero/one, with matching-width kernels.

Every schedule-comparison result and both 64-bit halves of each of the six block
answers contribute to the final condition. Generation becomes 2; health is 1
only when every comparison succeeds and 2 otherwise. The Option discriminant
separately distinguishes an admitted (possibly quarantined) ARM owner from a
pre-admission rejection. MSRV stores to padding contain public test data; they
are not secret material or an erasure guarantee.

The `bcmp` trampoline and complete `memcmp` body are reviewed, not assumed opaque.
They compare unsigned bytes across the specified length and return zero only
for equality. Their early exit on a mismatch is appropriate here because all
startup material is public; this does not qualify them for secret comparisons.

## Binding and regression controls

`aes_accelerated_startup_arm.py` requires exact startup/comparator symbols and
disjoint executable extents. It replays the existing complete hardware expansion
and round-kernel reviews and binds every call by width, name, address and bytes.
It pins all startup/comparator instructions and encodings. Local branch offsets
remain pinned. Unknown code cannot pass by obtaining a new hash during a run.

`startup-arm-reference.json` is a fixed copy of the already reviewed sequential-key
startup schedules and FIPS 197 plaintext/ciphertext values. It is not extracted
from the binary or regenerated by the checker. ADR and ADRP/ADD materializations
must agree with the actual encoded destinations and immutable mapped bytes.
Only their relocation bits normalize; instruction/register roles remain pinned.
The three direct vector loads are independently bound by the existing ARM
observer. No writable or out-of-file mapping is accepted for expected data.

Every instruction is replaced and every code byte flipped, including both
comparison helpers. Every distinct referenced data byte is also flipped and
must be rejected by the image reviewer. Synthetic tests mock policies only
within tests and cannot approve production bodies.

Each fresh unmodified executable must pass before negative execution. Then
624 separate schedule-byte mutations and one mutation in each of the plaintext
and three ciphertext inputs are executed in isolated temporary binary copies.
All 628 must return the exact quarantine marker after observing an admitted,
generation-2 quarantined owner and rejected session. A crash, pre-admission
rejection, healthy state, fallback or missing marker fails the check. The
original executable is never patched, and its hash is rechecked afterward.
The retained report records every case and tool/binary hashes.

Run with:

```sh
brynja-verify run aes --needed --category aes-linked-arm-startup
```

The optional capture-only mode is diagnostic and cannot emit the success marker.
These are software mutation tests, not voltage/clock/laser/EM fault experiments.
No claim covers arbitrary caller inlining, native timing, physical protection,
exception-table dispatch, or registers/spills. See the
[development ledger](aes-acceleration-development.md) for remaining work.

## Apple capture-only follow-up, 2026-11-11

The same runner now accepts `--mode apple-native --capture-only` on a real
Darwin ARM64 host. It builds for `aarch64-apple-darwin`, uses Mach-O symbol
capture without invented ELF sizes, and does not select the Linux musl linker.
Static admission first executes a baseline-compiled ISA probe; hosted admission
builds with `-Ctarget-feature=-aes`. The existing package-external startup
fixtures are unchanged. For example, on the Apple builder:

```sh
python3 scripts/aes/check-aes-accelerated-startup.py \
  --toolchain 1.99.1 --admission hosted --mode apple-native --capture-only
```

All sixteen configurations on the Apple M2 Pro completed: both compilers,
static/hosted admission, direct/facade routes and abort/unwind. The fixtures
check healthy startup, wrong-architecture rejection, all three cached key
widths, round trips, clearing and explicit terminal quarantine. Hosted cases
also exercise portable requests and wrong-architecture prefer/require behavior.
An isolated non-inlined startup symbol is retained in each executable.

The [capture record](../../assurance/aes-native-observations/v0.27.3/apple-startup-capture-20261111.json)
binds the previous development source/package identities, runner and fixture
hashes, native executable/tool hashes, metadata, disassembly and logs. Local
replay checked the exact configuration population, dependency graphs, package
hashes, ARM64 Mach-O headers and completion markers. This is an unauthenticated
development observation, not certification evidence or a current machine-review
pass. Original source remains an uncommitted working tree based on the recorded
commit. No timing measurements were collected.

Capture-only does **not** execute corrupted-answer or missing-feature controls.
The runner refuses Apple machine-review mode; Linux ELF startup policies cannot
approve Mach-O. Review of the Apple startup bytes, comparisons, bound callees,
feature detection and platform lifetime guarantees remains open. Existing Apple
caller reviews apply to their earlier retained binaries, not automatically to
these newly linked executables.

Three added runner tests cover host/mode rejection, the baseline probe, both
capture routes, and failure on missing execution markers or tool/executable
diagnostics without success JSON or a review pass marker. All 14 startup tests
and 897 integrated tooling tests pass. The unchanged Linux hosted current-
compiler review also passed four emulated consumers, 2,512 corrupted-answer
quarantine executions and eight missing-feature controls after this runner
change. No production Rust or publication gate changed.

The subsequent [static Apple startup review](aes-apple-static-startup.md) checks
the eight retained static bodies, their constants, kernels and declared system
`memcmp` bindings. A separate native follow-up passes all eight static binaries,
eight unchanged re-signed positives and 5,024 corrupted-answer quarantine controls.
It does not alter the original capture-only record or close hosted detection
and platform lifetime admission. See the
[native controls](aes-apple-static-startup.md#native-quarantine-controls).
