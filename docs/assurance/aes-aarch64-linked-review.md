# Retained native AArch64 final-linked helper review

This is a bounded instruction review of the native AWS collection described in
[`aes-native-observations/v0.27.2`](../../assurance/aes-native-observations/v0.27.2/README.md).
It covers eleven portable AES helpers, six surviving secret-output wrappers,
their copy routine and zeroizer in each of sixteen GNU/Linux AArch64 ELF executables:
Rust 1.90.0/1.99.1, direct/facade imports, abort/unwind, and the linked-operation
and caller-lifecycle fixtures. Each uses opt3, fat LTO, one codegen unit and
overflow checks. In the eight linked-operation KAT executables it additionally
covers six public-consumer boundaries and their six production constructors.
Those twelve bodies are not claimed reviewed in the separate lifecycle ELFs.
The eight lifecycle executables additionally have six focused caller-cleanup
bodies reviewed, including their unwind landing pads where present. The four
unwind executables also bind the resume import to its ELF relocation and PLT.
It is not whole-application or universal constant-time approval.

## Reproduction and evidence boundary

```sh
brynja-verify run aes aarch64-linked-helpers-review
```

This **offline** check consumes the original source and ELF/disassembly archives
under `target/`, whose digests are recorded in the native observation JSON. It
does not connect to AWS, rebuild a binary or rerun a timing experiment. Missing
artifacts fail, rather than being downloaded or silently replaced. Preserve the
local bundles before clearing `target`. They are deliberately not large Git files.
The registration fingerprints the small digest manifest, not generated `target/`
files. Each execution verifies archive bytes against that manifest. A recorded
pass describes the review already performed; it does not promise that local
bundles remain available after a build-directory cleanup.

Before review, the runner compares the original source snapshot byte-for-byte
with the current manifests, lockfile, all selected package files in the 21-crate
packaging closure, the public library fixture and both executable fixtures.
A source mismatch invalidates this retained-artifact replay. The original native
run remains a direct-script observation; this new check records only review of
those retained artifacts, not a newly performed native run.

All sixteen executables and all symbol/disassembly files must match the recorded
hashes and exact configuration population. Each reviewed function is decoded in
full, with contiguous four-byte instructions and exact symbol boundaries. The
printed words are compared to bytes in a unique, executable, file-backed ELF load.
Overlapping load segments, invalid extents, duplicate symbols and wrong targets
are rejected. The compiler, disassembler, symbol tool and observation record are
trusted inputs; these are not authenticated execution receipts.

## Policies and address binding

`aarch64-linked-review.json`, `aarch64-linked-wrappers-review.json` and
`aarch64-linked-public-review.json` and `aarch64-linked-cleanup-review.json` pin normalized
instruction text and encoding. The direct/facade, abort/unwind and fixture
variants share normalized helper policies per compiler, except for the MSRV
expansion epilogues: abort/unwind exchange the positions of two independent
restoring loads. Those variants have separate, panic-profile-bound fingerprints.
Policies are not regenerated by the checker.

- Local branch destinations must agree in the encoded displacement, numerical
  destination and same-symbol annotation. Their offsets remain in the encoding
  fingerprint. Only fixed in-function instruction boundaries are admitted.
- Each substitution call must target the exact inverse symbol in that executable.
  Its signed `BL` displacement is checked before masking the layout-dependent
  bits. The inverse body itself is reviewed in the same pass.
- Each `ADRP` page is calculated from the encoded signed page displacement and
  instruction address. Its sole `LDR D/Q` consumer must agree in register, vector
  width and scaled offset. Intervening use/clobber of the page-base register or
  control flow across a pending page is rejected.
- Constant bytes must come from a unique read-only file-backed load. GNU AArch64
  places these pools in an RX load, so R and RX are admitted; writable mappings
  are not. Actual constant bytes replace the address in the text policy before
  masking only the relocation-dependent page/load displacement bits.
- Every other operand and encoding bit remains bound. Unbound address/control
  forms fail. The exact fingerprints, not a broad opcode whitelist alone, are
  the acceptance condition.

Per-function mutation controls exercise text deletion/substitution, disassembly
bytes, ELF bytes, coordinated encoded-byte changes, branch destinations, inverse
call binding and constant bytes/page destinations. Expansion/transform controls
also alter each callee binding, scratch pointer, clear length, clear call and
loop-bound instruction. Wrapper controls remove every call site, immediate clear
length, successful owner tag/metadata store, and alter each callee binding.
Copy controls remove loads, stores, counter steps and working-register clearing.
The 4,240 helper/wrapper controls across the sixteen binaries, plus 9,120 public
boundary/constructor controls in the eight KAT binaries, 3,864 caller-cleanup
controls and 532 resume-import controls must fail (17,756 total).
The latter delete every instruction twice: once in text only, and once using a
coherent NOP replacement in text, instruction bytes and ELF bytes. This includes
every success guard, output store, clear/copy length, pointer setup and cleanup
call. Each callee binding and a truncated stream are also rejected.
Caller-cleanup controls likewise delete every instruction twice. Import controls
change every one of the 128 PLT instruction bits, consistently in the ELF and
printed instruction words, plus the GOT relocation, relocation type, symbol
binding, imported name and relocation-table linkage in each unwind executable.
Separate synthetic tests exercise malformed ELF and
disassembly, archive admission, current-source matching and registry scope.
The copy regression additionally flips every one of its 672 instruction bits
with matching ELF-byte changes; none is accepted under the pinned policy.

## Inverse and round primitives

| Helper | Rust 1.90.0 instructions | Rust 1.99.1 instructions | Control/address observations |
| --- | ---: | ---: | --- |
| Field inverse | 596 | 598 | No branch or call; fixed stack save/restore; current compiler additionally loads one public eight-byte constant |
| AES-128 round-key addition | 10 | 10 | One public schedule-offset bounds branch; fixed 16-byte load/XOR/store |
| Wide round-key addition | 164 | 164 | Sixteen public length/offset checks; byte loads/stores at fixed state offsets |
| Substitution | 474 | 213 | Public direction selection; exactly sixteen inverse calls per selected direction; 32 static call sites |
| Mixing | 206 | 159 | One public direction branch; no calls; fixed state offsets and six/four public shuffle constants |

### Field inverse

The MSRV stream is the previously reviewed scalar library stream with its four
callee-save pairs moved to the prologue. All arithmetic instructions and their
order otherwise match. The frame is 80 bytes; only fixed save/restore addresses
are used. Arithmetic stays in registers; there is no state-dependent branch or
memory index.

The current compiler vectorizes the initial field-multiplication stage. A fixed
eight-byte pool `0100040008001000` supplies halfword masks 1, 4, 8 and 16. `DUP`,
lane inserts, `AND`, `CMEQ` and `BIC` select arithmetic terms in registers, then
`FMOV`, fixed shifts and XORs reduce them into the scalar continuation. This is
not a secret-indexed memory table. The remainder matches the scalar library
arithmetic sequence after this transformed stage. Neither stream claims to clear
all arithmetic registers or all caller/compiler spills.

### Round-key addition

AES-128 computes the public round offset (`round << 4`), rejects offsets at or
above 176, then loads the selected 16-byte schedule block and fixed state block,
XORs them and stores the state. The final comparison supplies the error result.
The public round validity contract belongs to callers, which are not closed by
this helper review.

The wide helper matches the reviewed library stream exactly after local-label
and immediate-notation normalization. Sixteen separate public bounds checks
guard schedule-byte accesses. State offsets are fixed 0 through 15. Secret
schedule/state bytes are arithmetic operands, not address or branch operands.

### Substitution and observed residual spills

The MSRV helper's normalized text equals the previously reviewed scalar library
policy. Direction selects a fixed unrolled path; every byte has one inverse call
and the appropriate fixed affine arithmetic. The current helper vectorizes the
affine operations but still calls the inverse separately for all sixteen bytes.
The direction branch depends on the public parameter, not the state bytes.

**Current-compiler residuals:** the 144-byte frame has `x29 = sp + 48`. The
inverse-direction path stores the affine-transformed 16-byte state at
`[x29 - 16]` (sp + 32) across inverse calls. The forward-direction path spills
six inverse results into fixed slots spanning sp + 12 through sp + 35 before
assembling its vector result. These slots are not zeroed by the helper's epilogue.
They may hold sensitive block intermediates. Caller-owned buffer clearing must not be
described as erasing these compiler-created copies. The saved-register frame,
vector registers and residual stack data remain outside that erasure claim.

### Mixing and register shuffles

The direction selects a fixed forward or inverse path. State loads and stores
stay within the 16-byte block at public fixed offsets. The compiler groups the
GF arithmetic into vector lanes using fixed shifts, adds, compares and XORs.
`TBL` acts on register-held data with indices loaded from fixed public constants;
it is not a state-indexed load from a memory S-box.

All observed shuffle bytes are pinned, including out-of-range selector bytes
used to zero lanes. The MSRV forward path uses five pools and its inverse path
one; the current forward path uses three and inverse path one. The checker binds
each actual pool to its instruction and does not trust a disassembler's nearest
symbol annotation as the identity of that constant.

## Expansion, complete transforms and their zeroizer

| Body | Rust 1.90.0 instructions | Rust 1.99.1 instructions |
| --- | ---: | ---: |
| AES-128 expansion | 134 | 137 |
| AES-192 expansion | 149 | 150 |
| AES-256 expansion | 199 | 175 |
| AES-128 transform | 112 | 110 |
| AES-192 transform | 114 | 112 |
| AES-256 transform | 114 | 112 |
| Volatile region zeroizer | 5 | 6 |

Expansion admits exactly 16/24/32 input bytes before loading the key or writing
the schedule. AES-128's public byte counter starts at 19, advances by four and
stops at 179 after writing through schedule byte 175. AES-192 generates 46 words
after its initial 24-byte copy: its negative public counter reaches carry after
46 increments, ending at byte 207. Its reciprocal multiply/modulo-by-24 phase
selection depends on the public schedule position, not key bytes. AES-256's
counter starts at 35, advances by four and stops at 243 after writing byte 239.
Its public phase selects rotate/SubWord/Rcon at multiples of 32 and SubWord at
the halfway point. All key-dependent operations are fixed arithmetic or calls
to the reviewed field inverse; none selects a branch or memory address here.

The MSRV uses scalar-lane widening for some four-byte scratch loads. Rust 1.99.1
uses a vectorized affine transform for AES-256's halfway SubWord: four inverse
results enter fixed halfword lanes; byte duplication, constant shifts and XORs
implement the rotations, with `0x63` in each lane. Fixed lane extraction and
packing return the four bytes. It does not introduce a memory lookup table.

Every admitted expansion finishes with the exact bound zeroizer call over four
bytes at `[x29 - 4]`. **Both compilers' final-linked AES-192 expansion additionally
spill an affine intermediate at `[x29 - 8]`**, sp + 24 through sp + 27 in a
128-byte frame. The four-byte clear covers sp + 28 through sp + 31, not this
spill. This remains a concrete limit of the clearing guarantee; source-owned
scratch erasure does not erase every compiler-created key-equivalent copy.

Transforms select encrypt/decrypt using the public direction bit. The reviewed
loops implement 10/12/14 rounds and public schedule offsets, including initial
and final AddRoundKey without MixColumns in the final round. AddRoundKey errors
branch on the reviewed helper's public bounds result. The wide variants differ
by their 208/240-byte schedule extent, final-key offset 192/224 and round count;
their call identity is separately bound to the wide helper. Role admission
checks those final-key offsets and the generic width when encoded in the symbol.

ShiftRows uses a register-table shuffle with fixed **public** selector bytes:
`00050a0f04090e03080d02070c01060b` forward and
`000d0a0704010e0b0805020f0c090603` inverse. These bytes are checked in the ELF,
not inferred from the nearest disassembly label. The public selectors occupy
sp + 0 through sp + 15. Each 16-byte temporary state copy at sp + 16 through
sp + 31 is cleared after its use, before subsequent calls/error exits. Every
transform has four static zeroizer call sites, including the two final rounds.
Register-held copies remain outside this claim.

The exact `brynja_core::secret_memory_volatile::zeroize_region_volatile` symbol
is required uniquely in the symbol inventory and its mapped body is reviewed
alongside every caller. It returns for zero length; otherwise it decrements the
public length, stores a zero byte, advances the pointer and loops. The MSRV
uses a post-indexed store; the current compiler uses a store and separate add.
There are no calls, secret loads or secret-dependent addresses in this body.
This establishes the observed stores to the admitted region, not physical RAM,
cache, register or compiler-spill erasure.

## Surviving secret-output wrappers and transfer

Seven additional bodies are reviewed in every executable: `Aes128Key::transform`
(68 instructions), `Aes128ExpandedKey::transform` (52), `Aes192Key::transform`
(58), `Aes256Key::transform` (59), the two wide `secret` specializations (67 on
MSRV, 66 on current), and `brynja_core::secret_memory_transfer::copy_bytes` (21).
Exact owner names and unique, nonoverlapping extents are required. Opaque MSRV
wide-secret names are resolved by their single exact call to the reviewed
AES-192 or AES-256 transform. Current generic symbols must agree with that width.
Every bound callee is reviewed in the same executable; no external PLT call or
unbound tail call is admitted in these bodies.

Raw-key wrappers clear all sixteen admitted output bytes before expansion. Their
operation-local schedules are initialized and cleared over exactly 176/208/240
bytes. A cleared key owner supplies an empty slice to expansion, whose reviewed
length check fails before loading the key. AES-128 transforms a separate 16-byte
stack state and copies it to output only on success. Success installs the
output pointer/length and zero success tag; failure installs an error tag and
clears output. Normal success and transform failure clear the state; both
success and expansion/transform failure clear the local schedule.

The cached AES-128 wrapper clears output first, rejects an absent schedule or
length other than 176, and uses a separate cleared 16-byte state without
re-expansion. Rust 1.99.1 folds the pointer/length admissions into `CMP/CCMP` and
one branch: an incorrect length forces the failure condition, as does a null
pointer with the correct length. It does not branch on key or state bytes.

Wide raw-key wrappers pass an initialization guard to their secret helper. Its
ELF-bound metadata constant is sixteen bytes encoding length 16 and initialized
count 0: `10000000000000000000000000000000`. The guard's pointer comes from the
admitted output, not this constant. The secret helper clears the state on all
reviewed return paths. After successful AES computation it checks guard presence,
checked-add overflow for the 16-byte fragment and destination capacity before
copying. Only exact complete initialization installs the returned owner. A
failure or incomplete finish clears the whole live destination region. The
current compiler removes the dead initialized-count store after the copy; the
equality check still precedes ownership publication.

The wide raw-key wrappers' abort/unwind variants exchange two independent
conditional-select instructions and use `CBZ` versus `TBZ #0` for expansion's
reviewed boolean error result. The current AES-128 raw-key unwind variant also
uses `TBZ #0`. These are separately pinned, not normalized away. The six
surviving linked bodies contain no unwind landing pads or runtime imports;
this review does not infer complete exception-table/unwind qualification from
their absence or transplant the library artifact's unwind policies.

The call-free, stack-free copy routine consumes the public length in eight-byte
chunks and then single bytes. Every access uses a public bounded offset. Its
normal return explicitly clears working registers x4/x5/x6 and sets flags to a
fixed comparison; x0/x1 are pointers, not copied payload. The body matches the
existing AArch64 inline-assembly transfer implementation. Caller-side register
copies, interrupted execution and unrelated spills remain outside its erasure
claim. This adds no production assembly or unsafe code.

## Public-consumer boundaries and constructors

The eight KAT executables retain six explicit `linked::public{128,192,256}` /
`linked::cached_public{128,192,256}` consumer boundaries. Exact symbol identities,
all six called production constructors and nonoverlap with the other reviewed
bodies are checked. The 23 distinct normalized policies are pinned by compiler
and panic profile. Direct and facade routes match. There are no constant loads
or unwind landing pads in these twelve bodies; no exception-dispatch conclusion
is inferred from that absence.

The raw constructors each have 21 instructions: clear the destination, copy
exactly 16/24/32 key bytes through the reviewed core routine, then publish the
pointer, length and success tag. The MSRV abort build interleaves a restoring
load with the tag store; other configurations store the tag first. These distinct
streams are pinned without masking the difference.

Cached constructors have 45/46/47 instructions. They clear caller schedule storage
(176/208/240 bytes), initialize a separate stack schedule, then expand the
16/24/32-byte key. An expansion error installs the error tag and clears both
stack and destination schedule; success copies the complete schedule, installs
the caller-owned clearing owner and clears the stack schedule. No raw key copy
is added. AES-256 uses a 288-byte frame; AES-128/192 use 224/256 bytes.

Raw public boundaries have 67/65/66 instructions on the MSRV and 66/64/65 on
the current compiler. Constructor failure exits without touching public output.
After admission, expansion uses a zero-initialized stack schedule. Failure clears
that schedule and the live key owner. Successful expansion stages the 16-byte
input immediately after the schedule and calls the matching transform with
public direction zero. `TBNZ w0, #0` skips the sole public vector store on failure.
Both transform outcomes clear the staged block, schedule and live key storage.
For 128/192/256-bit keys the block is at sp + 176/208/240, respectively.

Cached public boundaries have 50 MSRV or 49 current instructions. They check
constructor success, owner presence and exact 176/208/240-byte schedule length,
stage the block at sp, then call the matching transform. The same boolean
success guard precedes the only public vector store. Both transform outcomes
clear the staged block and the live cached schedule; invalid-owner/length paths
skip publication and clear a present owner.

The current compiler replaces the MSRV's 32-bit result-tag load/compare/branch
with a 64-bit zero-tag check. AES-256 also swaps output/key pointer registers;
wide epilogues reorder independent restoring loads. All affected operand and
branch differences have their own reviewed fingerprints. These are normal/error
return observations, not claims of complete stack or register erasure.

## Caller cleanup and unwind imports

The six focused lifecycle boundaries take ownership of a secret block and a
raw key or cached schedule, invoke a caller-provided callback, then drop both
owners. Their names and extents must be unique and must not overlap any other
reviewed body. All six widths share the same instruction pattern within a
compiler/profile, except for a public completion marker (16/24/32/176/208/240).
The marker is not the clearing length: clearing uses the admitted owners'
pointer/length metadata.

Abort bodies contain 30 instructions. They preserve owner metadata on the stack,
transfer the callback through the fixture's `black_box` slot and invoke exactly
one `BLR x8`. Normal return checks block presence and clears its region first,
then checks key/schedule presence and clears that region. Only then does the
boundary return its public completion marker. This does not claim cleanup when
the process aborts. The compiler endpoints differ in stack-slot placement, not
the ordering of these clears.

Unwind bodies contain 48 instructions, using 64-byte MSRV or 80-byte current
frames. Their normal path performs the same block-then-key clearing. The emitted
landing pad saves the incoming exception pointer in x19, checks and clears the
block owner, then checks and clears the key/schedule owner, restores the exception
pointer to x0 and calls `_Unwind_Resume`. There are two static resume sites and
four static zeroizer sites, covering the presence/absence branches. Callback
selection is trusted caller input, not secret-dependent dispatch. Callback
admission is explicit in this checker: exactly one `BLR x8` with matching
encoding is permitted; other review scopes still reject indirect calls.

For each unwind executable, the checker parses bounded, file-backed `.dynsym`,
`.dynstr`, `.rela.plt` and `.plt` sections and binds them to ELF loads. It requires
the symbol, string and relocation addresses, sizes and entry formats to match
the live `PT_DYNAMIC` import-table tags consumed by the loader, not just section
names. Missing, duplicate, inconsistent or unterminated dynamic metadata fails.
It requires
one undefined global function named `_Unwind_Resume` with a unique AArch64
`JUMP_SLOT` relocation and zero addend. The exact four-instruction PLT entry
(`ADRP x16`, `LDR x17`, `ADD x16`, `BR x17`) must address that relocation's writable
GOT slot, with matching encoded and printed operands. This establishes the
identity of the imported dependency, not the runtime value placed in the GOT
or the correctness of the external unwinder. Dynamic-loader/interposition policy
remains a deployment trust boundary.

The native caller-unwind observations exercise dispatch separately. This review
does not validate exception tables, the loader, libgcc unwinding or every possible
caller body. Small synthetic ELF and instruction fixtures exercise the review
without requiring the local AWS archives; no native timing campaign is rerun.

## Still unfinished

Other final-linked inlined secret-output entry points and the lifecycle fixture's
constructor copies are outside the reviewed body set. Arbitrary caller cleanup
and external unwind dispatch are not qualified by the focused boundary review.
The library-artifact policies are not transplanted onto those linked bodies.
Native correctness and the existing first-order timing results remain separate
observations, not substitutes for emitted-code review.

This review does not prove instruction latency on other processors, higher-order
leakage absence, power/EM resistance, physical-fault detection, complete spill or
register erasure, hostile-host protection, or every downstream build. It adds no
mandatory HSM requirement and no new publication gate.
