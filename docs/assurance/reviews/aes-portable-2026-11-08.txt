Findings

All are Low or Informational. Most are documented limitations that matter under a military or physical-access threat model.

1. No fault-injection countermeasure in the block primitive

- Severity: Low here, but Medium if the deployment includes physical or glitch attackers.
- Location: crates/brynja-crypto/src/aes/portable.rs:95-123, portable/wide.rs:60-89, and the public encryption paths aes.rs:196-209 and aes/wide.rs:103-112.
- Type: Missing defence against fault attacks.
- Description: A single computation releases ciphertext. One induced fault in rounds 8–9 lets a fault analysis recover an AES-128 key from very few faulty ciphertexts. This is documented ("does not detect physical arithmetic faults"), but for a defence product it is the main gap left in an otherwise complete primitive. The encrypt_block_public path, which releases ciphertext externally, is where a check would help most.
- Remediation (optional hardened path: decrypt again and compare in constant time before releasing):
portable::transform(&mut state.0, &schedule.0, false)?;
let mut check = Scratch::<16>::new();
check.0.copy_from_slice(&state.0);
portable::transform(&mut check.0, &schedule.0, true)?;
if !brynja_core::constant_time::bytes_eq(&check.0, input) {   // existing CT helper
    return Err(Error::SecretMemory);                           // output untouched
}
output.copy_from_slice(&state.0);
  This roughly doubles the cost, so put it behind a feature flag or a separate *_verifie

2. The public-ciphertext acknowledgement can be created anywhere

- Severity: Informational.
- Location: crates/brynja-crypto/src/aes.rs:63-68.
- Type: API design (declassification is in name only).
- Description: PublicCiphertext::acknowledge() is a pub const fn that any code can call, so the type documents intent but enforces nothing. That is acceptable as a speed bump. It should not be described in
  assurance documents as an access-control boundary.
- Remediation: Either document it as advisory only, or make it non-const and #[must_use]r, for example acknowledge_public_release(reason: &'static str), so call sites are easy
  to grep.

3. Clearing cannot reach register and scalar copies

- Severity: Informational.
- Location: portable.rs:80 (let (x, y, z, w) = …), the field arithmetic temporaries, and.
- Type: Secret data may remain in memory.
- Description: This is correctly documented. Spilled stack slots from multiply/inverse can hold intermediate state bytes after return. The AArch64 and x86 fingerprint checks only confirm the instruction
  stream; they do not show that spill slots are empty.
- Remediation: If you need stronger guarantees, add a stack-scrubbing call at the API boundary for high-assurance builds, sized from the maximum frame the assembly review already measures:
#[inline(never)] fn scrub_stack() { let mut s = [0u8; 512]; clear_owned_region(&mut s).o); }

4. The AArch64 constant-time evidence is compile-time only

- Severity: Informational.
- Location: scripts/aes/check-aes-aarch64-dataflow.py:116-118, assurance/aes-native-obse
- Type: Limit of the side-channel assurance scope.
- Description: The review checks --emit=asm from the --lib rlib. With fat LTO, final code generation happens at link time, so the reviewed instructions are not necessarily what ships. This is stated ("not
  native or final-linked qualification"). The fixed-versus-random experiment is first-orithout SMT, boost or CPU isolation.
- Remediation: Before you claim AArch64 side-channel qualification, run the linked-binary review that x86 already has and native timing on the target hardware.

5. Timing-experiment noise threshold is loose

- Severity: Low (affects the assurance tooling only).
- Location: scripts/aes/check-aes-fixed-random.py:23 (MAX_CV = 1.0).
- Type: Statistical method.
- Description: A coefficient of variation up to 100% still counts as conclusive. Each saon, volatile clearing and Drop, so a small round-level effect can disappear in thatnoise. With t ≥ 4.5 and no multiple-comparison correction across 39 campaigns, a pass means "nothing detected", not "no leak".
- Remediation: Tighten the threshold (for example MAX_CV = 0.25). Add a sensitivity control: one campaign with a deliberately inserted secret-dependent delay that the test must flag, so a pass is shown to
  mean something.

6. AVS fixtures are pinned to repository hashes, not checked against NIST originals

- Severity: Low.
- Location: scripts/aes/check-aes-avs.py:17-24, assurance/aes-avs/README.md.
- Type: Supply-chain provenance.
- Description: The checked hashes are of the CRLF→LF-normalized files. The NIST zip hashes appear only in the README, and no tool re-derives the normalized files from the zips. Practical risk is very low: forging a self-consistent 1000-step MCT chain would require a matching faulty AES, and catch it.
- Remediation: Add an offline re-derivation script that, given the original aesmct.zip/azip hashes, normalizes the files and compares them with the pinned HASHES.

## Security boundaries that remain important

This candidate is a complete implementation of its claimed AES single-block scope, not a complete secure encryption protocol. It does not provide an authenticated mode, nonce management, message framing, or a TLS key schedule. That limitation is accurately documented in RELEASE_NOTES_0.27.2.md (release-notes/RELEASE_NOTES_0.27.2.md:9).

It also does not establish military deployment approval, physical side-channel resistance, fault-injection resistance, complete register/spill erasure, FIPS 140-3 validation, or independent cryptographic review. The repository explicitly preserves those limitations in VERIFICATION_STATUS.md (docs/VERIFICATION_STATUS.md:115).
