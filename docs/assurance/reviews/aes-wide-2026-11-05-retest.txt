New items, both Low and both in test tooling only

1. The oracle hash covers the wrong file. scripts/aes/check-aes-differential.py hashes /usr/bin/openssl, which is a small front-end. The AES code actually used is in libcrypto.so.3, so the log line "oracle identity: unchanged" doesn't cover the code doing the comparison. The doc does say dynamic libraries are trusted, but the log line reads stronger than that. To fix it:
   - Add LD_PRELOAD, LD_LIBRARY_PATH, LD_AUDIT and OPENSSL_ia32cap to FORBIDDEN.
   - Also hash the resolved libcrypto, for example:
FORBIDDEN = (..., 'LD_PRELOAD', 'LD_LIBRARY_PATH', 'LD_AUDIT', 'OPENSSL_ia32cap')
libcrypto = next(Path(l.split('=>')[1].split()[0]).resolve()
                 for l in subprocess.run(['ldd', str(executable)], capture_output=True,
                                         text=True, check=True).stdout.splitlines()
                 if 'libcrypto' in l and '=>' in l)
# record and compare digest(libcrypto) before/after, like the executable
2. One IR-checker rule was relaxed. scripts/hmac/hmac_engine_scratch.py now accepts an output guard passed in as a function argument instead of a local allocation. I checked how it is used: only the AES shared-secret role enables it. That role first requires a noalias dereferenceable(24) %destination argument that is never redefined, and HMAC callers keep the old strict rule. This is sound; just keep it from being enabled anywhere else without the same checks.

Unrelated to this change: clippy without --no-deps fails on brynja-hash-sha3 with the 1.99 lint chunks_exact_to_as_chunks. That crate hasn't changed since v0.27.0 and CI uses --no-deps, so it doesn't block anything. It will start failing if CI drops --no-deps or the dependency lints get stricter.

## Remaining finding

- Severity: Medium
- Location: scoped_release.py (scripts/release/scoped_release.py:54)
- Vulnerability Type: Review-to-release TOCTOU / incomplete evidence binding
- Description: The release gate verifies that a committed pentest report says PASS, but it does not bind that report to a reviewed commit or tree hash. After a PASS report is committed, later production-code commits could retain the old report and still pass candidate(), provided the worktree is clean. GitHub checks bind automated tests to HEAD, but the manual security review does not.
- Current impact: Not presently exploitable in the workflow because security/pentest/v0.27.1.md is absent, so the final gate correctly refuses this candidate. This weakness predates the update, but the new release-gate tests do not close it.
- Remediation: Use a two-commit workflow: commit the reviewed candidate, then add a report containing Reviewed-Commit, allowing no production changes after that commit.

def reviewed_commit(version: str, raw: str, root: Path) -> None:
    values = re.findall(r"^Reviewed-Commit: ([0-9a-f]{40})$", raw, re.MULTILINE)
    if len(values) != 1:
        raise ValueError("pentest report requires exactly one Reviewed-Commit")

    reviewed = git(root, "rev-parse", f"{values[0]}^{{commit}}")
    report = f"security/pentest/v{version.removeprefix('v')}.md"

    changed = set(
        git(root, "diff", "--name-only", f"{reviewed}..HEAD").splitlines()
    )

    # The post-review commit may add only its disposition.
    if changed - {report}:
        raise ValueError(
            "production or assurance code changed after the reviewed commit"
        )

For stronger assurance, require the review commit or detached report to be signed by an approved reviewer key.
